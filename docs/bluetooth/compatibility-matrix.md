# Bluetooth compatibility register (EVL-139)

**Version:** 0.1.0 discovery baseline  
**Reviewed:** 2026-09-29  
**Physical devices confirmed:** none

This register separates platform API capability from compatibility of the actual POS devices. No cashier, kitchen, or manager device models, OS/browser versions, Bluetooth chipsets, or minimum OS versions were supplied. Therefore, every real device combination remains **unknown / not accepted** until recorded and tested with two physical devices while Wi-Fi and internet are disabled.

## Go/no-go summary

Pure PWA Bluetooth does not meet the two-device requirement across the proposed mobile platforms: Web Bluetooth is central-only, and WebKit does not implement it. The concrete mobile fallback is a **Capacitor-wrapped Karma UI plus a project-owned native BLE bridge**: Swift/Core Bluetooth on iOS and Kotlin/Android Bluetooth LE APIs on Android. Capacitor documents iOS and Android as native platforms and exposes custom native plugin APIs; no desktop platform is included in this selected route. Keep web application/domain code shared; keep scan/advertise, GATT, permission, lifecycle, and secure-key operations native. A first cross-platform pairing + one command-batch sync spike is estimated at **8–12 engineering days**, followed by **2–3 days of device-pair acceptance and fixes** once target hardware is named. This is a planning estimate, not a commitment or a tested result; exact target hardware/OS can change it. A macOS/Windows POS target requires a separate host/extension decision and estimate. ([Capacitor documentation](https://capacitorjs.com/docs))

Android's official overview documents central and peripheral as separate BLE connection roles and the GATT-server API. Apple documents central scanning/connection and local peripheral services/advertising. Both support the native route at framework/API level; neither source guarantees a specific unknown handset supports stable simultaneous Karma use. Native scopes must request only the permissions needed for foreground pairing and state why they are needed. ([Android BLE roles](https://developer.android.com/develop/connectivity/bluetooth/ble/ble-overview), [Android server role](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer), [Apple central](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager), [Apple peripheral](https://developer.apple.com/documentation/corebluetooth/CBPeripheralManager))

## Evidence needed to turn a row green

For each cashier/kitchen/manager device, capture make/model, OS version/build, BLE hardware capability, app container/browser version, power/battery condition, permission result, whether advertising and scanning work in the foreground, and whether the OS suspends the app during sync. Pair the actual two devices with Wi-Fi and internet disabled. Record operator steps, peer identity confirmation, batch size, observed throughput, interruption/resume, duplicate retry, distance/obstructions, elapsed time, battery change under a repeatable procedure, and any OS dialogs. A native API smoke test, simulator, mock transport, or Chrome-to-accessory demo is not this evidence.

Until that evidence exists, no actual device is marked compatible, the two-device acceptance criterion remains open, and no physical range/power claim is made.
