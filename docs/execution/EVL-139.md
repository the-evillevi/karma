## Checkpoint

EVL-139 asks for a device/OS go/no-go matrix, a versioned message/state/error contract, an order transfer between two actual devices with Wi-Fi/internet off, duplicate suppression, and observed pairing/range/permission/battery behavior. No target device inventory was supplied, and no physical devices were available to test. The first three documentation artifacts are therefore a protocol/design draft, not evidence that Bluetooth has been implemented or acceptance passed.

## Research result

Chrome's Web Bluetooth documentation describes websites in the GATT central role; this does not expose a peripheral/server role to a second PWA. WebKit lists Web Bluetooth among APIs it has not implemented. Apple's native Core Bluetooth has central and peripheral managers; Android documents BLE central APIs and `BluetoothGattServer`. These are platform API capabilities, not compatibility guarantees for unknown point-of-sale hardware. See the linked official sources in [`docs/bluetooth/compatibility-matrix.md`](../bluetooth/compatibility-matrix.md).

## Decisions to preserve

- Use one complete immutable `CommandBatchDocument` per transfer and preserve the original EVL-113 identities, actor/device metadata, event order, and payload snapshots.
- Require explicit foreground pairing, paired-device authorization, standard reviewed authenticated key exchange and AEAD, session sequence/replay checks, and platform-protected key storage. No cryptographic authentication or encryption is implemented or tested in this checkpoint.
- Treat receiver ACK as durable local peer receipt only. Peer-transfer receipts are separate from the EVL-114 server-sync outbox; an ACK never drops a backend-pending batch.
- Do not elect coordinators from RSSI/timestamps. EVL-113's single active register writer remains the authority; other stations submit only role-authorized preparation events. Exact policy must align with EVL-114.
- EVL-114 RLS requires uploader `auth.uid` to match original `actorId`, with the original `deviceId` belonging to that actor. Each originating actor/device must sync its authored batch; do not rewrite identities, use service credentials, or share actor login. Cross-actor upload would require a reviewed signed-relay endpoint and authorization contract in EVL-140.
- Do not mark the Linear issue Done, update Linear, claim supported device models, or start EVL-140 from this work.

## Current file scope and verification

The matrix/protocol draft is in `docs/bluetooth/`; isolated codec and tests are in `src/bluetooth/`. No application entry point, package manifest, lockfile, Linear issue, physical device, Bluetooth adapter, or external service was changed or accessed. `node --test src/bluetooth/protocol.test.js src/domain/order-domain.test.js` passes. Tests cover canonical JSON, size/event/depth bounds, current batch identity/lease metadata, derived event IDs, event metadata consistency, and session-envelope/sequence guards. They make no claim about authentication, encryption, crash durability, GATT transport, or two-device acceptance. Root requested re-review of this fixup.
