The migration stores active membership and display names, one replaceable actor session per enrolled logical device, and owner-only membership/device RPCs. `append_command_batch` derives the actor from `auth.uid()`, rechecks membership, current session, capability and lease, validates bounded event envelopes, and enforces the role/action matrix before an immutable insert. Direct authenticated command inserts are denied.

## Secure POS implementation

The app now has distinct demo and secure entry paths. Secure mode requires explicit Supabase URL/public key, branch and device configuration; it fails closed instead of displaying the demo seed as a verified identity. An individual Supabase sign-in must bind to a server-authorized role and device lease. The client rejects malformed, mismatched or expired contexts, closes authority on known server denials, and rejects stale mutation callbacks. PIN unlock is available only without network and only for an identity previously verified on the same branch/device; online access requires a new server check. If PIN storage fails, the UI keeps the verified online session but does not claim that the PIN was saved.

The shared POS remains mounted when the operator switches identity, preserving the current order and its original actor attribution. Actor-specific command queues remain attached to the original identity. UI visibility and component mutation boundaries use the shared role policy; they are useful local gates, while authoritative durable writes still depend on EVL-126's server-backed command integration. Client storage is not a trusted audit store and local PIN verifiers do not resist someone with access to browser storage or developer tools. Logical device binding is not physical-device attestation, and offline revocation is observable only after reconnect.

Owner administration can link an existing Auth UUID through the membership RPC or request a new individual Auth identity through `owner-provision-user`. The Edge Function verifies the caller's JWT and active Dueña membership, creates the identity without sending an invitation/email, assigns its branch membership, compensates by deleting the new identity if assignment fails, and returns a one-time temporary password only on success. The service-role key stays server-side. The function and actual new-account workflow are not deployed or hosted-tested in this checkpoint. The one-time password is shown in memory only; PWA activation is blocked until the owner explicitly closes that view or switches identity.

The current POS keeps its reviewed kitchen, cashier, captured-price, manual-payment and shared responsive UI flows. Reprint callbacks remain simulated; no physical print or server reprint audit is claimed. Durable POS writes, conflict handling and reconnect proof remain EVL-126 work. Recovery, backup and operational enrollment drills remain open.
