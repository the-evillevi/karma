# EVL-118 — secure identity and role access

Status: early server-policy checkpoint for root review. The migration is draft only; it has not been applied to any local or hosted database. The combined app remains an isolated seeded demo and must not be presented as a production identity system.

## Reviewed baseline and intended authority

The EVL-114 schema already stores branch roles and device capabilities, but authenticated clients could insert command batches directly under a coarse device policy. The new append-only migration adds active membership state and display names, one replaceable actor session per enrolled logical device, and owner-only membership/device RPCs. It replaces the direct command insert grant with `append_command_batch`, which derives the actor from `auth.uid()`, reloads the active role and device session from service-owned rows, checks the current cash-register lease, validates bounded event envelopes, and applies the role/action matrix before the single immutable insert.

Dueña can manage membership rows and revoke a device; Encargado, Barra and Mesero cannot administer accounts. Membership administration applies to an existing `auth.users` identity. Creating or inviting an Auth identity remains a private administrative provisioning step; this web client has no service-role key and the seeded demo PINs are not converted to real accounts. Reprinting a ticket or preparation slip is restricted to Dueña or Encargado, requires a reason, and must record the actor. The present POS still uses simulated print callbacks; physical printing and its server audit path are not implemented or claimed by this slice.

The database permits order opening for active branch roles; Dueña, Encargado and Barra can complete sales; order cancellation, preparation cancellation, and discounts require Dueña or Encargado and a bounded reason; menu edits and inventory adjustments require Dueña or Encargado. Other preparation transitions are available to active operations roles. Report/history rows are limited to owners/managers or an operator's own records, so the POC does not give Barra or Mesero a report query path.

## Device, offline and identity-switch limits

`register_device_sessions` binds an authenticated user to one enrolled logical device session. It replaces the prior session for that device; every remote write rechecks the current user membership, device, session, capability and lease. This is not physical-device attestation: an authenticated user who copies the device ID and session bearer value can imitate that browser. A browser PWA cannot securely attest a physical terminal. Production deployment still needs reviewed enrollment/session binding and operational recovery.

Offline PIN unlock and identity switching are not wired in this checkpoint. The implementation must only unlock identities whose server role/device binding was previously cached on this installation, must preserve the current draft when switching identities, and must clearly mark offline work as not yet server-authorized. An offline browser cannot learn about a new revocation; when online, revoked/inactive identities must have cached authorization cleared and new sync attempts stopped. PIN hashes stored by a browser are a convenience barrier, not hardware-backed protection against an operator with developer-tools or filesystem access.
