# EVL-127 recovery and synchronization status — bounded UI slice

This checkpoint replaces simulated recovery/synchronization claims with read-only status and export guidance for the storage currently wired to the POS.

## Current behavior

- Secure POS state is still written by the existing browser `localStorage` adapter, scoped by branch/register key. A visible device-network status is separate from server receipt; the UI reports the latter as unknown.
- The screen records the result of the latest local browser write observed by the POS. A failed write shows a warning. Checkout does not show its successful result until the browser write succeeds; if that write fails, the result blocks payment retry and tells the operator to inspect the report before charging again.
- Existing string entries in `pending` are preserved as unverified legacy labels. They are not described as committed commands, exposed for retry, cleared by a sync action, or converted to server acknowledgements. Existing `conflicto` evidence remains visible and continues to block affected order actions.
- The Demo connectivity control only changes a simulated network indicator. It never contacts a server, clears labels, or reports synchronization success.
- The recovery guide is available to roles with `viewReports`. Its button uses the current permission check before opening Reportes. The existing protected CSV export is the available manual report export; it contains dated sales/payment/compensation evidence for the selected period, not a complete POS backup.
- No automatic backup schedule, 03:00 backup record, seven-day retention claim, forced-sync action, or CSV import/restore flow is provided.

## Limits and next boundary

The secure screen has not been connected to the EVL-126 durable journal, command receipt, retry, or recovery APIs. Until that integration exists, the screen cannot prove remote receipt, retry safely, or restore the entire business state on the same device. Do not treat the CSV as an application backup: it omits open accounts and station drafts, kitchen preparation state, inventory/catalog configuration, customer ledger, users/identity, settings, and journal/remote state. Browser-local data can still be lost if browser storage is cleared or unavailable.

A later same-device full export/restore must be built against the validated durable journal/storage contract. It needs an owner-controlled, integrity-checked full-state package and a tested restore path that preserves actor/audit history, unresolved conflicts, and pending operations. This checkpoint deliberately adds no whole-state import, no simulated retry, and no server-write claim.
