# EVL-116 — engineering foundation checkpoint

Status: bounded foundation implementation ready for root review. Existing legacy screens remain outside the strict TypeScript boundary, so this does not claim application-wide type safety or completion of every EVL-116 acceptance item.

## Architecture decision

Keep the existing Vite + React multi-page app and add a production-only PWA build config. The three existing documents (`/`, `/comanda.html`, and `/offline-demo.html`) remain entries. The POS rewrite, catalogue model and full RxDB persistence remain in their later issues. EVL-114's RxDB/Dexie command-batch prototype remains the storage experiment; this checkpoint adds the cached application shell rather than migrating legacy screens to RxDB.

The shared order domain, offline command boundary, update-safety state machine, application roots, and error boundary are strict TypeScript. They preserve MXN integer-centavo amounts, captured price/tax/modifier snapshots, event identity and independent financial/preparation state. `src/domain/order-domain.js` remains as a compatibility re-export for existing JS/CLI consumers while the implementation lives in `.ts`. The legacy `.js`/`.jsx` screens remain unchecked by TypeScript and ESLint; this is incremental adoption, not a claim that the whole POS is typed. ESLint gates the typed boundary, and Prettier gates the foundation code and relevant execution docs.

## PWA and offline behavior

`vite.config.pwa.js` composes the established Vite config, retaining its HTML inputs and private-fixture deny list. Run `pnpm build:pwa` to produce a production service-worker build. Set `KARMA_BASE_PATH=/karma/` when building for a path-prefixed host such as GitHub Pages; the manifest, icon, scope, start URL, navigation fallback and Vite asset base follow that prefix. Root-hosted preview/prod uses the default `/`.

`pnpm test:pwa:e2e` serves the built production artifact on an isolated strict port. A real Chromium persistent profile first visits the online shell, verifies a Workbox precache, closes and reopens the browser context, disables network access, then loads POS, Comanda and the offline-demo document. This establishes cold navigation from a previously warmed cache when browser assets are available. It does not establish first-ever installation while offline. Service-worker updates wait in a prompt state. The operator control requires explicit confirmation and blocks while POS checkout, order capture, product/user editing, report detail, dialogs, or PIN entry is active; Comanda and offline-demo report their own safe states. Confirmation is invalidated on any intervening safety-state transition, and the UI reloads only if the application is still safe after activation. If state cannot be verified, the operator must close the station safely and reopen it later. The browser test exercises a real POS user editor and proves the update remains blocked until that editor is closed.

The offline-demo's EVL-114 behavior is still a prototype. Offline capture is conditional on a previously verified, unexpired logical lease; the browser's physical device is not cryptographically bound. Cached app documents do not make Supabase-dependent sign-in or server reads available offline. Legacy POS/Comanda state remains localStorage-based until its dedicated persistence work.

## Environment and secret handling

`.env.example`, `.env.preview.example`, and `.env.production.example` contain placeholders only. Keep local settings in ignored `.env.local`; configure preview and production through the hosting provider's private environment settings. Every `VITE_` value is delivered to the browser, so only the Supabase URL and public anon/publishable key belong there. Service-role credentials are server/administrative only and must never use a `VITE_` name or be included in static hosting. The existing `.env.offline-test.local` private test fixture remains excluded from Vite's filesystem server and ignored by Git. `pnpm check:client-bundle` scans generated files for a private test service-role value if that ignored fixture exists, a CI canary, and recognizable service-role markers; it reports no credential values.

The quality workflow has no Supabase project secrets and does not deploy. It runs install-from-lockfile, format, lint, typecheck, domain and typed-boundary tests, regular build, bundle scan, PWA build, and a real-browser cached-shell/update test. Root verified the combined integration preview separately; after merging this foundation branch, root should repeat the hosted URL/base-path check against the final combined build.

## Diagnostics and migrations

`safeDiagnostic` maps known storage, permission, conflict, network, and server failures to generic Spanish guidance. Unknown errors receive a fixed `UNCLASSIFIED` code; arbitrary SDK codes and raw messages are never returned. A React error boundary covers each app entry and renders only generic guidance plus an allowlisted diagnostic code. The production-browser test injects an error containing a synthetic e-mail and key and verifies neither appears in the rendered interface. This protects the UI from displaying server payloads or tokens; it is not a substitute for structured, redacted operational telemetry.

Database migrations remain immutable, ordered SQL files under `supabase/migrations/`. For local development, apply and test on a disposable local project. For remote work, review the exact migration diff and checksum, apply to a disposable preview project first, validate RLS with positive and negative role/device cases, and retain the migration history. Never edit an applied migration; add a forward migration. Production schema changes require a backup/restore plan, owner-reviewed rollout and post-migration checks. Event-envelope `schemaVersion` and RxDB collection schema/migration versions are separate concerns; both need explicit compatibility/replay tests before changing persisted formats. EVL-114's current hosted proof was performed independently by root against the separate test project; this checkpoint makes no production-schema changes.
