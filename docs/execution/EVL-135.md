# EVL-135 customer profile and account checkpoint

This checkpoint adds the local customer profile and account-management slice. It does not complete the customer-credit milestone or production acceptance.

## Implemented in this branch

- Dueña and Encargado can create, update, and archive minimal customer profiles with a required display name and optional phone. Archiving preserves the append-only statement and is allowed only when debt and prepaid balances are both zero.
- Dueña and Encargado can view profiles, derived debt/prepaid balances, and account statements. Only Dueña can set an approved credit limit; a new profile starts at zero, and lowering a limit below current debt is rejected.
- Dueña and Encargado can record manually reported debt repayments and prepaid receipts with amount, reason, actor, time, payment method, and reference. The receipt status explicitly remains `operator_reported_unverified`; the UI does not claim to verify external settlement.
- Profile and account commands use stable IDs, current-role checks, per-customer revisions, strict persisted-ledger validation, and local save-before-success. A failed write remains retryable, identical retries do not duplicate entries, corrupt history fails closed, and command commits preserve newer unrelated saved POS state.
- Profile/account maintenance and statement access use their own permissions. This checkpoint does not define whether a cashier may select a customer during checkout; it adds no checkout customer selector or balance disclosure. A future selector needs its own narrowly scoped permission and sanitized balance lookup.

## Explicitly pending

- Checkout credit charges and prepaid applications are not exposed. They require the atomic payment/order/customer transaction and retry contract in EVL-126.
- Local records remain pending synchronization. Cross-device conflict resolution, server authority, durable settlement evidence, and production acceptance remain open under EVL-126 and related gates.
- Existing anonymous sales or balances are not imported or attributed to named customers. Operators must not treat this ledger as historical migration or verified payment evidence.
- Corrections/reversals have no operator UI in this slice. The domain retains them as append-only operations for a separately reviewed workflow.
