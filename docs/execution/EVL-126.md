# EVL-126 — Durable local POS journal

**Status:** phase 1 local journal checkpoint. The secure POS UI is not connected to this journal, and no remote POS sync is implemented.

Applied server checkpoints now support only the open/edit order family and its open-only cash read. A separate forward candidate is under review for owner/manager discount and order cancellation. That candidate is not applied and does not connect the POS UI or journal to remote writes.

## Phase 1 contract

The production journal opens a separate IndexedDB database derived from the verified branch and register-device identifiers. Actor identity is kept on every immutable command, but is deliberately not part of the database name so that switching staff does not hide another actor's pending work. The demo RxDB database remains separate. This code does not verify an identity or grant authority; callers must supply the current secure access context and pass the existing action checks before making a command.

The only supported version-1 action is `order.snapshot.saved`. Its payload is a complete draft/open-order snapshot with stable order and line IDs, captured product and modifier names/prices/tax versions, table/order type/customer fields, centavo totals, and capture time. `branchId`, `deviceId`, `actorId`, `commandId`, `occurredAt`, `expectedRevision`, and `schemaVersion` are part of the immutable command contract.

An IndexedDB read/write transaction validates the target order's complete immutable history, head, and saved projection against deterministic replay before checking a command ID or selecting the next revision. It then writes the immutable command, next revision, and deterministic order projection together. The projection is not returned until the transaction commits. Identical retry content returns the original command only after this integrity check; changed content with the same ID raises `LOCAL_COMMAND_ID_CONFLICT`. A stale expected revision is retained in `revisionConflicts` with a bounded diagnostic code and rejected as `LOCAL_REVISION_CONFLICT`; it cannot silently replace the current projection. IndexedDB serializes overlapping read/write transactions across tabs, and a unique aggregate/revision index is a second guard. Startup replay validates all commands in the configured branch/device scope and verifies that persisted heads and projections exactly match replay, failing closed on missing, orphaned, malformed, out-of-scope, or mismatched derived rows.

The local database also has durable stores for server receipts, blocked commands, revision conflicts, and allow-listed diagnostics. Recording a receipt atomically removes any active block for that command, so its queue state is unambiguously acknowledged; a later block for an acknowledged command is rejected. The receipt API only stores a record supplied by a caller; phase 1 makes no server call and creates no receipt by itself. Integration must write a receipt only after the future authenticated server RPC returns an acknowledgement. Diagnostic rows accept only an identifier, kind, safe code, time, and optional command ID; they reject free-form messages and credentials.

Each live journal connection is cached by both the IndexedDB factory identity and scoped database name. On `versionchange` it closes and removes itself from that cache, so a later open creates a fresh connection. A blocked open rejects; if IndexedDB later completes that request, its late connection is closed. The adapter opens schema version 1 only and rejects a newer stored database version without attempting a downgrade.

## Explicitly unsupported in phase 1

- Secure POS draft/open-order UI integration, payment/checkout/tender/tip/change, refunds, and reversals.
- Discounts as an authorized/audited mutation, cancellation, preparation, reprint, menu edits, stock adjustments, table configuration, or inventory compensation.
- Account split/move/merge, multi-aggregate atomic commands, a conflict-resolution UI, and shared operational read models.
- Remote sync, authenticated reconnect, retry/backoff coordination, server-side idempotency proof, or a claim that any local command has synced.
- Importing old localStorage data as verified commands, recovery/export UI, or restoring an account from local browser data.

The order snapshot can carry a discount total, but it does not assert who authorized that discount or preserve its reason. It must not be treated as a discount event. Payments and every other unsupported mutation remain on their current paths until separately integrated behind the approved command contract.

The journal stores offline order/customer data in the browser's IndexedDB profile. It does not store Supabase tokens, service keys, passwords, or credential responses. Branch and device IDs are hashed into the database name; scope is also checked on every append. This storage boundary supplements the verified access/action checks in the application and is not an authorization boundary by itself.

## Compatibility checkpoint (phase 2, adapter only)

The current POS persistence model is not a valid `order.snapshot.saved` payload. Existing open lines may have captured names and prices without a catalog price-version ID or tax rate; current tax data is often absent. Closed sales also use a smaller line shape and can omit product IDs, line IDs, subtotal, discount, or split lineage. The adapter must preserve observed values with explicit provenance and represent missing facts as unknown. It must never invent a price version, tax rate, discount reason, actor, or split relationship to satisfy the typed phase-1 command.

The compatibility snapshot is a sanitized read/restore contract, not a journal command or migration. It is versioned, scoped to branch/device, and requires the caller's stable capture-request ID so retries can keep the same snapshot identity. It allowlists order, open-account, kitchen-preparation, sale, tender, cancellation, split, and compensation fields. It excludes authentication/session data, staff rosters and PINs, and one-time credential responses. Monetary values are safe integer cents and are validated against the source record's available reconciliation facts. Fields the prototype did not capture remain null/unknown with provenance instead of being inferred.

The adapter does not connect the journal to POS mutations. A draft-only restore is unsafe once checkout, cancellation, split, refund, or kitchen work has occurred, because replaying only the draft can recreate an account that was already closed or omit an immutable payment/compensation. Keep all current mutation paths unchanged until the full state transition is represented atomically.

## Reviewed/applied server lifecycle checkpoint

The next forward migration adds only `order.discounted` and `order.cancelled` to the reviewed server command boundary. Both actions require a current Dueña or Encargado session and a nonblank reason. A discount retains equal authorized/allocated cents, reason, actor, timestamp, and command identity. It fails closed when any captured line total is unknown or the cumulative discount exceeds subtotal. Once an order has a discount, line edits that make subtotal unknown or reduce subtotal below that discount reject without changing the order. Cancellation is terminal and preserves captured lines, discount entries, cancellation metadata, and audit history.

The candidate adds `read_pos_order_lifecycle_v1` with an explicit feed version. It carries a cancelled order as a tombstone while the existing open-only read retains its shape for undiscounted orders and fails closed with `ORDER_LIFECYCLE_READ_REQUIRED` for a visible live discount it cannot represent. The feed is a live delta stream, not a full startup snapshot; consumers would need to merge by order ID and highest revision. Preparation-linked orders, split, checkout/payment, refunds, catalog/tax verification, and POS/UI wiring remain unsupported. No production durability or sync claim follows from this slice.

The disposable PostgreSQL proof forces a late projection-write failure for both discount and cancellation, verifies command/event/sequence/head/projection/history rollback, then retries the identical command ID and receives one commit. It also checks unknown-price and cumulative over-discount rejection, terminal-feed retention, and rejection of malformed stored history. Root reviewed/applied the exact forward migration only to isolated karma-pos; all 10 actual hosted role, lifecycle, parity, creator-privacy and concurrency cases passed without skips in 35.6 seconds. See EVL-126-lifecycle.md for the immutable hash and remaining gates.

For checkout records that include both the legacy lossy `items` list and captured `lineSnapshots`, the adapter keeps the captured IDs, product IDs, captured price/tax evidence, notes, and modifier facts, and checks them against the legacy display facts and quantity. It also preserves the recorded `mesa`, preparation folio/shared flag, and legacy audit display tuples as captured; it does not manufacture audit IDs or timestamps. Explicit non-MXN values and conflicting cent aliases are rejected. Compensation allocations are checked against complete captured payment identities, including method and cumulative return limits. When legacy payment identity is unavailable, the captured allocation remains as-is with `allocationEvidence: partial`; no payment identity is inferred.

## Multi-aggregate durability plan (future checkpoints)

1. Freeze versioned event shapes for order open/edit/discount/cancel, split source and child, shared preparation, completed sale, tenders/change/tips, refund/void allocations, and inventory compensation. Each command binds the original actor, branch, device, stable command ID, and expected revisions for every touched aggregate. Unknown catalog/tax facts remain explicit; applied EVL-114/118 SQL is immutable.
2. Add a forward server schema and RPC that checks current membership/device authority and all expected revisions, then appends the complete command and updates read projections in one transaction. Define least-privilege shared kitchen/account reads separately; the existing raw-batch access policy is insufficient.
3. Add local IndexedDB transactions over every participating aggregate. Persist the immutable command and deterministic projections before showing success. Use transaction-level revision checks across tabs; do not rely on an in-memory queue. A split touches source, child, and preparation lineage; checkout touches the account, sale, payment/tender facts, and operational views; compensation appends allocations without rewriting the captured sale or payment.
4. Restore by replaying and validating the complete order, sale, kitchen, and compensation state. Reconnect uploads the original command under its original actor only after that actor reauthenticates; record receipts only after authenticated server acknowledgement, and retain authorization or revision conflicts for intervention.
5. Wire one mutation family at a time only after its complete local replay and server atomicity tests pass. Acceptance still requires hosted offline-close-reopen recovery, idempotent acknowledgement, revocation, role checks, and conflict retention. This compatibility checkpoint makes no durability or sync claim.
