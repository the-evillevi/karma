# EVL-126 — Durable local POS journal

**Status:** phase 1 local journal checkpoint. The secure POS UI is not connected to this journal, and no remote POS sync is implemented.

## Phase 1 contract

The production journal opens a separate IndexedDB database derived from the verified branch and register-device identifiers. Actor identity is kept on every immutable command, but is deliberately not part of the database name so that switching staff does not hide another actor's pending work. The demo RxDB database remains separate. This code does not verify an identity or grant authority; callers must supply the current secure access context and pass the existing action checks before making a command.

The only supported version-1 action is `order.snapshot.saved`. Its payload is a complete draft/open-order snapshot with stable order and line IDs, captured product and modifier names/prices/tax versions, table/order type/customer fields, centavo totals, and capture time. `branchId`, `deviceId`, `actorId`, `commandId`, `occurredAt`, `expectedRevision`, and `schemaVersion` are part of the immutable command contract.

An IndexedDB read/write transaction checks the command ID and aggregate head, then writes the immutable command, next revision, and deterministic order projection together. The projection is not returned until the transaction commits. Identical retry content returns the original command; changed content with the same ID raises `LOCAL_COMMAND_ID_CONFLICT`. A stale expected revision is retained in `revisionConflicts` with a bounded diagnostic code and rejected as `LOCAL_REVISION_CONFLICT`; it cannot silently replace the current projection. IndexedDB serializes overlapping read/write transactions across tabs, and a unique aggregate/revision index is a second guard. Startup replay sorts by aggregate revision and fails closed on missing revisions.

The local database also has durable stores for server receipts, blocked commands, revision conflicts, and allow-listed diagnostics. The receipt API only stores a record supplied by a caller; phase 1 makes no server call and creates no receipt by itself. Integration must write a receipt only after the future authenticated server RPC returns an acknowledgement. Diagnostic rows accept only an identifier, kind, safe code, time, and optional command ID; they reject free-form messages and credentials.

## Explicitly unsupported in phase 1

- Secure POS draft/open-order UI integration, payment/checkout/tender/tip/change, refunds, and reversals.
- Discounts as an authorized/audited mutation, cancellation, preparation, reprint, menu edits, stock adjustments, table configuration, or inventory compensation.
- Account split/move/merge, multi-aggregate atomic commands, a conflict-resolution UI, and shared operational read models.
- Remote sync, authenticated reconnect, retry/backoff coordination, server-side idempotency proof, or a claim that any local command has synced.
- Importing old localStorage data as verified commands, recovery/export UI, or restoring an account from local browser data.

The order snapshot can carry a discount total, but it does not assert who authorized that discount or preserve its reason. It must not be treated as a discount event. Payments and every other unsupported mutation remain on their current paths until separately integrated behind the approved command contract.

The journal stores offline order/customer data in the browser's IndexedDB profile. It does not store Supabase tokens, service keys, passwords, or credential responses. Branch and device IDs are hashed into the database name; scope is also checked on every append. This storage boundary supplements the verified access/action checks in the application and is not an authorization boundary by itself.

## Remaining EVL-126 gates

1. Root review this local adapter checkpoint before UI wiring.
2. Freeze the server payload, command types, aggregate concurrency/version contract, and least-privilege open-order/kitchen read API in a forward migration. Applied EVL-114 and EVL-118 migrations are immutable. The current EVL-118 RPC allowlist and raw-batch read policy are not sufficient for all POS mutations and shared waiter/barista work views.
3. Map the secure POS draft/open-order path to `order.snapshot.saved`; make UI success wait for local commit and restore the active order from replay at startup. Do not convert legacy localStorage into a verified command.
4. Integrate checkout, kitchen, cancellation, menu and inventory only with their owner-approved contracts and actor/reason checks. EVL-189 split needs an atomic multi-aggregate server operation; root owns that integration.
5. Add authenticated remote sync only after the forward schema is reviewed. Keep pending work when network is unavailable, require the original actor to reauthenticate before upload, record receipts only after server acknowledgement, and retain authorization/version conflicts for intervention.
6. Prove a real offline PWA sale, close/reopen recovery, exact-once server acknowledgement, revocation handling, role matrix, conflict retention, and protected diagnostics against the isolated hosted project before calling the acceptance complete.

## Phase 1 verification

- `pnpm test:domain` — pure validation and deterministic replay.
- `pnpm test:pos-journal:e2e` — Chromium IndexedDB persistence across browser-profile restart, branch isolation, actor-preserving pending queue, duplicate/conflicting command IDs, injected local write failure, two-tab revision serialization, conflict retention, and receipt/block/diagnostic record persistence.

The receipt e2e case uses a synthetic stored acknowledgement fixture to exercise the local format only. It does not exercise a server, network, or sync path.
