# EVL-126 preparation-family server proposal

## Scope and recommendation

Add server support for `preparation.sent`, `preparation.transitioned`, and `preparation.cancelled` as a forward-only migration after the reviewed order-lifecycle migration is applied. Keep this as an atomic server/domain checkpoint; do not wire the UI, advertise durable kitchen sync, or claim sale/payment recovery. Continue to leave EVL-114, EVL-118, and applied EVL-126 migrations byte-identical.

Reuse the private `pos_operation_commands`, `pos_operation_aggregate_events`, `pos_operation_aggregate_heads`, and `pos_operation_projections` tables. Extend the action allowlist and strict validators; do not introduce a client-authored after-state or a second journal. Add a preparation queue read RPC with a new versioned shape. The existing open-order and lifecycle feeds remain unchanged apart from the separately reviewed fail-closed legacy discount guard.

## Contract facts from the current reducer

- `preparation.sent` payload is exactly `{ orderId, preparationId }`. It requires an existing open order with no preparation link and a new preparation ID. The server creates a revision-1 `queued` preparation whose `originOrderId` and sole `linkedOrderIds` entry are the order ID, whose lines are an exact clone of current order lines, and whose creator/time/history are derived from the verified actor and command envelope. The order revision also increments, sets `preparationId`, and appends the send command to order history.
- `preparation.transitioned` payload is exactly `{ orderId, preparationId, nextStatus }`, with `nextStatus` only `preparing`, `ready`, or `served`. `preparation.cancelled` is exactly `{ orderId, preparationId }` plus a mandatory bounded reason. Both require the order/preparation link. Only the preparation projection/revision advances; the order is a read-guard and does not gain a history event.
- Allowed status paths are queued→preparing→ready→served, with cancellation from queued, preparing, or ready. Served and cancelled are terminal. Do not allow skips, repeats, reopening, or cancelling an already-terminal ticket.
- Order cancellation is independent: it must preserve a linked ticket without cancelling it. The current reducer permits later valid preparation transitions even when the linked order is cancelled. Conversely, a new ticket cannot be sent from a cancelled order.
- Order line edits synchronize a single active linked ticket by copying the complete new line array and incrementing both order and preparation revisions. They reject shared preparation and terminal tickets. They do not append a preparation history item. Until the server supports this exact two-aggregate line-edit behavior, reject all three line mutation actions when `preparationId` is non-null; silently leaving the kitchen snapshot stale would violate reducer parity. Shared-preparation/split remains unsupported.
- A linked ticket may exist when an order is discounted or cancelled. The lifecycle validator must accept the link and leave prep state intact. No server split, checkout, refund, inventory, customer-account, or preparation-line editing claim follows from this slice.

## Authority and device matrix

Every append and identical retry must first re-resolve `auth.uid()`, active branch membership/role, current bound session, device, capability, and (for cash devices) active matching lease through `require_register_context`. Never use command-supplied role, actor, capability, lease, or device as proof. Check action permission before command-ID lookup so revocation/demotion cannot use an old command as a success oracle. Existing PT409/HTTP409 revision conflicts remain conflicts; do not map them to `40001` or auto-retry business commands.

| Action | Role permission | Device capability | Notes |
| --- | --- | --- | --- |
| send ticket | `openOrder`: Dueña, Encargado, Barra, Mesero | `cash_register` | It links/copies a financial order projection; send is not the legacy `PreparationStarted` transition. Cash lease required. |
| transition ticket | `prepareOrder`: all four roles | `cash_register` or `preparation` | A preparation device has the `no-cash-lease` sentinel and never receives order/contact/money reads. |
| cancel ticket | `cancelPreparationWithReason`: Dueña or Encargado only; reason required | `cash_register` or `preparation` | Matches EVL-118 `PreparationCancelled` authority. |

EVL-118’s legacy started/ready/served events allow the four roles on cash or preparation devices, while its cancellation branch restricts cancellation to Dueña/Encargado on either capability. `read_only` must be denied for every mutation. Keep the capability checks separate from role permissions: in particular a prep-only device cannot use `preparation.sent` to create/link a cash order.

## Atomic append and replay

1. Strictly validate schema version, command envelope, action-specific payload, bounded reason, canonical UUID-like identity fields as already required by v1, and an exact expected-revision array. Reject extra/missing/null keys and every unsupported action. Session/lease is transport authentication and stays outside the immutable business command/hash.
2. For send, require exactly canonical refs `{order@currentRevision, preparation@0}`. For transition/cancel, require both `{order@currentRevision, preparation@currentRevision}` even though only preparation advances; this protects the link and the order’s terminal/link state. Sort/lock every touched or guarded head in the repository’s canonical `(branch, kind, id)` order.
3. Serialize a new preparation ID safely even when its head does not yet exist (unique branch/kind/id constraint plus a transaction-local rev-0 reservation/placeholder or equivalent). A competing use of the same ID must fail as a conflict without revealing another order’s projection.
4. Read/validate current server projections under locks, derive next state with the same business rules as `applyPosOperation`, then atomically insert one immutable command, append the appropriate event row(s), allocate one branch sequence, and update all affected heads/projections. Send writes an order and preparation event at the same server sequence; transition/cancel writes one preparation event and advances only that head. No partial head/projection/sequence/receipt may survive a late failure.
5. Exact retry returns the saved receipt only after the current-authority/action checks and exact command-content comparison. Changed-content reuse of an ID conflicts. Historical replay validates immutable envelopes and deterministic state only; it must retain committed prep history after current role revocation rather than reauthorize old events.
6. Keep send/ticket lines server-derived from the locked order projection, never trust line content in the command. Validate prep link, exact origin/link IDs, revision/history identity, allowed status transitions, line bounds, and all reciprocal order references. Prep history command ID may lag its head revision after line synchronization because reducer line edits alter prep revision without adding a prep history entry; validators must model that explicitly rather than equating history length and revision.
7. Preserve terminal order facts: canceling an order leaves its prep aggregate and history intact; later preparation progress remains allowed. A terminal prep ticket remains in projection and is never silently removed or reopened.

## Forward migration and feed shape

Use a new migration (suggested next slot `20260930000400_evl126_preparation_v1.sql`) to replace only forward-facing constraints, validators, append/read functions, and grants. Add a strict private preparation validator; permit non-null `order.preparationId` only when it resolves to the matching preparation projection; validate one-to-one links for this slice; and reject shared links. Extend `assert_order_projection` so cancelled and discounted linked orders remain valid. Reject line-added/changed/removed against an already-linked order with a stable unsupported-family error until atomic prep line synchronization lands. Keep all tables in `pos_private`; authenticated/anon must have no schema/table privileges. Do not expose the raw command or projection tables.

Add a sanitized `read_pos_preparation_queue_v1(session, lease, cursor, limit)` which derives branch/device from the current session and permits only active `cash_register` or `preparation` sessions with a role allowed to prepare. It returns ticket ID, revision, status, safe item/quantity/modifier labels, order/preparation lineage identifiers needed to correlate the ticket, and a server cursor. It never returns customer name/phone/address, table, line/sale money, discounts, tax, currency/catalog facts, payment facts, actor IDs/rosters, reasons, raw commands, credentials, or session/lease material. The current `notes` field is unrestricted free text and may contain PII; safest v1 omits it until the product separates/labels kitchen instructions in the write contract. That means special instructions remain a known kitchen usability gap, not something to leak by assumption.

Include `served` and `cancelled` tickets as terminal facts in the delta feed so clients can remove them from active queues. Do not filter terminal rows out or turn them into absence. For initial recovery, cursor zero must yield latest state for all visible tickets, including terminals, across pages. Use a composite cursor `(server_sequence, aggregate_id)` or return every row at a boundary sequence before advancing; a sequence-only limit can skip siblings when a future command emits multiple preparation events. Feed responses are sanitized operational views, not full journal/projection restore and not proof of remote acceptance of local offline work. An audit-history RPC, if needed, should be a separate Dueña/Encargado-only surface.

## Acceptance and proof before any UI wiring

- Differential local Postgres vs TS reducer after-state/history for send, every legal transition, cancellation from each nonterminal status, prep progress after linked order cancellation, linked order discount/cancel, and rejection of unsupported line edits/shared prep. Verify exact status/revision/history and same-sequence dual events on send.
- Hostile payload tests: extra/missing/null keys, invalid statuses/reasons, wrong order/prep IDs, cross-branch refs, wrong expected-ref count/order/revision, client attempts to supply lines/role/actor/device/capability/after-state, duplicate prep IDs, stale heads, invalid role/device combinations, revoked membership/session/device/lease, and stale exact retry after revocation.
- Real transaction proofs: race two sends for one order and same new preparation ID; race transition/cancel with order cancellation and with line edit; one serialized winner and bounded PT409 loser, no partial command/event/head/projection/sequence. Force a late event/head/projection failure for send, transition, and cancellation, verify every table is unchanged, then verify byte-identical retry succeeds after the failure is removed.
- Authority matrix cases: all four roles can send from cash; only cash-capable devices send; all four roles transition from cash/prep devices; only owner/manager cancel with a reason on cash/prep; Mesero cannot cancel; read_only cannot read queue or mutate. Check online rebind/revocation before exact retry.
- Read privacy tests inspect raw JSON and ensure every forbidden field is absent, not merely null. Verify ticket terminal facts, initial cursor recovery, cursor paging with equal-sequence siblings, stale/ahead cursor rejection, and that the legacy open-order feed never supplies a discounted order without the lifecycle facts it omits.
- Root must review the exact migration hash, run disposable local PostgreSQL from immutable 114/118 plus all reviewed EVL-126 migrations, then run the hosted proof only against the approved isolated synthetic `.invalid` fixture. No hosted apply/deployment is part of this proposal.

## Dependencies / gates

The order-lifecycle migration and its post-discount legacy-feed guard must be reviewed/applied first. The TS reducer remains the executable parity reference. The journal’s local IndexedDB/replay work is not yet bridged to these RPCs, and server support alone does not provide restart-safe POS UI. Before any UI wiring, also implement and prove atomic multi-aggregate local append/replay for linked order+prep, line-sync or explicit UI blocking, and complete lifecycle/checkout/split/refund recovery. Keep manual payment, printer, menu, stock, and actual-account claims open until their respective server families and tests exist.
