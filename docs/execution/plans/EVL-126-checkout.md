# EVL-126 checkout/refund server-family proposal

Research date: 2026-09-30. Read-only review of the integration checkout at `/Users/evillevi/.codex/worktrees/karma-integration/karma`. This note proposes the next server family; it is not an implementation or production acceptance claim.

## Current contract and deployment boundary

The version-1 TypeScript operation reducer specifies `order.checked-out` and `sale.refunded` in `src/domain/pos-operations.ts:69-131`, but the applied server RPC rejects both. Forward migrations `20260930000100`, `20260930000200`, and `20260930000300` are recorded as applied only to the isolated Supabase `karma-pos` proof project (`vwvlsayxsunefeehiavt`), with exact hashes in `docs/execution/backend.json`: 00100 `38527549de19c9f19db43b79dcdc24f690c524df6c01e7cadfa2f8a34a973cab`, 00200 `8fef21b96d7881ea801e0f056cf1d1fbd8127d2a105093c21782030de034b140`, 00300 `06808e81f81d7ffd81daf38cc0191898e49aef817e8496f630b32cae6d21f6cc`. The recorded proof is 8/8 actual hosted cases after the 001/002 revision-conflict fix, then 10/10 actual hosted cases for 003 lifecycle; these establish only the documented families. The currently applied server boundary supports open/edit/details plus owner/manager discount and cancellation. Preparation, split, checkout, and refund remain rejected/unavailable (`docs/execution/contracts/pos-operations-server-v1.md:5, 57-61`; `docs/execution/EVL-126-server.md:3-7`; `docs/execution/EVL-126-lifecycle.md:3-9`). Backend metadata explicitly keeps `productionReady: false` and records no POS operational UI sync. The local operation journal is not integrated with `PosApp`; current secure checkout still saves a localStorage sale, and local saved records are not server receipts (`docs/execution/EVL-126-server.md:7`; `docs/execution/EVL-126-lifecycle.md:9`; `src/PosApp.jsx:1190-1272`). It must remain labelled local/receipt-unknown until the server append and full-state read/recovery path are wired and proven.

The applied EVL-114/118 `command_batches` RPC is a single-aggregate, older event format with no multi-aggregate heads/projections/revision transaction. Its raw command read policy is not a sanitized work view. The applied EVL-126 foundation already uses separate `pos_operation_*` tables/RPCs instead of widening or reusing that API (`docs/execution/contracts/pos-operations-server-v1.md:15-23, 25-39, 61-67`).

## Reducer and command shapes

The immutable command envelope is `{schemaVersion, commandId, branchId, actorId, deviceId, occurredAt, expectedRevisions, action, reason, payload}` (`pos-operations.ts:136-149`). Identity/session/lease/capabilities are intentionally split: actor/branch/device and command facts are immutable command identity; the current verified session, lease, membership, role, and device capabilities are passed out-of-band at append time (`pos-operations.ts:1-5, 151-158`; server contract `:38-47`). V1 strict validation allows only exact payload fields and canonical, unique, sorted aggregate refs, bounded to four refs (`pos-operations.ts:367-418, 1848-1875`).

Checkout payload (`pos-operations.ts:118-122`):

```ts
{
  orderId: string;
  saleId: string;
  payments: Array<{
    paymentId: string;
    method: "cash" | "card" | "transfer";
    netAmountCents: number;
    tipCents: number;
    tenderedCents: number | null;
    changeCents: number | null;
    recordMode: "manual";
    verification: "not-applicable" | "manual-unverified";
  }>;
}
```

The derived exact revision set is the current `order/orderId` revision, the new `sale/saleId` at revision `0`, plus the current `preparation/preparationId` revision when the order is linked to preparation. It is sorted by `compareRevisionRef`; the preparation is a read guard, not a changed aggregate. This is `expectedTouchedAggregates` at `pos-operations.ts:2086-2100`. Checkout advances only the order and sale, each exactly once; the order closes and sale starts at revision 1 (`:1190-1273`, general advancement check `:583-616`). If no preparation is linked, omit that ref. Client refs must equal the derived set exactly; the server must not trust a caller-supplied changed-aggregate list (`:2111-2126`; server contract `:45-47`).

Refund payload (`pos-operations.ts:123-131`) is `{saleId, refundId, allocations:[{paymentId,method,amountCents}]}` with a required envelope `reason`. Its exact ref set is only current `sale/saleId` revision (`:2102-2105`). A successful refund advances only that sale revision and appends a refund event; it does not change the order, reopen a sale, or rewrite the captured payments (`:1275-1343`). Refund identity is per-sale `refundId` plus global immutable `commandId` idempotency.

### Checkout transition rules already executable in TypeScript

`reduceCheckout` (`pos-operations.ts:1190-1273`) requires an open order and a previously unused sale ID. It refuses any line with no captured line total or `priceEvidence === "unknown"`; if a prep ID exists, the order/prep relationship must still be reciprocal (`:1201-1215`, link validator `:2170-2182`). It derives safe `subtotalCents` from captured `lineTotalCents`, totals authorized discount entries, and derives `netTotalCents = subtotal - discount`; due may be zero but cannot be negative (`:1216-1220`, `:2192-2223`). Payments' net cents must add exactly to that due; zero due requires zero payment rows and positive due requires at least one (`:1221-1234`). The sale copies the captured order lines, discounts, creator, type/table/customer, and `preparationId`, and records the closing actor/time plus subtotal/discount/net/tips/payments (`:1235-1262`). The order moves to closed and gets the checkout history event/time (`:1263-1272`). Preparation status/lines are left byte-for-byte unchanged, so checkout is deliberately separate from kitchen progress.

Each payment has exact field allowlists and safe non-negative integer cents. Cash requires both tendered and change and checks `tendered = netAmount + tip + change`; cash verification must be `not-applicable`. Card/transfer require null tender/change and `manual-unverified`, never a claimed processor verification (`:1797-1846`). Payment IDs are unique within the checkout and max 50 payments (`:1538-1549`). The reducer also safely sums the independent tip values (`:1225-1228`).

**Important model discrepancy to resolve in the bridge:** the current POS helper calls the total due `baseCents + tipCents`, and its legacy payment `netAmountCents` rows sum to that all-in amount; each legacy row also stores its allocated tip separately (`src/domain/payment-tender.js:46-117`; `src/PosApp.jsx:1147-1174, 1238-1261`). Operation-v1 instead defines `netAmountCents` as the amount toward the discounted order due, with `tipCents` separate: its example is `net=3000 + 2500 = sale.netTotal 5500`, tips 100+50, and cash tender `3300 = net 3000 + tip 100 + change 200` (`src/domain/pos-operations.test.ts:874-938`). For an existing legacy row, the bridge therefore needs to compute `operation net = legacy net - legacy tip`, retain gross cash tender/change/tip, and check translated payment nets equal `subtotal-discount`; do not copy/rename fields. Preserve the legacy sale's all-in `totalCents` as a captured legacy fact and make any `netTotal + tip` relationship explicit.

Operation-v1 records noncash gross manually as `netAmountCents + tipCents` because its tender/change fields are null for card/transfer. This remains manual evidence, not processor settlement. The current reducer validates each tip as safe non-negative cents and safely sums tips, but has no separate explicit gross-payment field or tip-to-food-due cap (`pos-operations.ts:1221-1228, 1813-1845`). Do not invent a tip cap as part of the SQL port: document the intended net/gross semantics, preserve the row-level tip allocations, and add differential cases (including a tip greater than the food portion) so TypeScript, SQL, and the legacy adapter agree. For cash, the existing row equation explicitly reconciles net + tip + change to tender.

### Price, discount and tax rules

Each captured line validates `baseUnitPriceCents + modifierTotalCents = unitPriceCents` when present, and `unitPriceCents * quantity = lineTotalCents`; modifier identities and captured modifier effects are validated (`pos-operations.ts:1604-1727`). Unknown price provenance cannot carry price amounts, while catalog-versioned prices require a product and catalog price version ID. A non-unknown legacy/prototype price is allowed for checkout (`:1626-1669, 1201-1209`), but IDs and labels alone do not prove the price is authoritative. The current server contract says to reject catalog-versioned claims until they are checked against a server-owned menu (`pos-operations-server-v1.md:51, 57-59`).

Order discounts are positive safe cents with a mandatory reason, owner/manager capability, and cannot exceed the captured line subtotal (`pos-operations.ts:329-350, 810-843, 1475-1479, 2192-2215`). The checkout sale snapshots each discount's original authorized and allocated amount, reason, actor and occurrence time. Split allocation can alter allocated discount distribution on child/source while preserving original authorization facts.

Tax is currently only a per-line captured metadata object (`currency/evidence/rateBasisPoints/amountCents/policyId`); validation enforces shape/provenance consistency but doesn't compute or reconcile it (`pos-operations.ts:1728-1757`). `lineSubtotal` and sale due use only line totals less discount (`:1216-1218, 2200-2223`); there is no sale-level tax total, tax policy computation, inclusive/exclusive flag, or authoritative tax schema. Therefore do not claim the checkout reducer calculates or verifies tax or invoice totals. Preserve tax snapshots exactly with `unknown`/prototype evidence and gate statutory invoice/report claims on an authoritative versioned tax family. EVL-189 also rejects a partial split of a line carrying an amount-only known tax because v1 has no tax amount basis (`:1003-1009`; test around `pos-operations.test.ts:1214`).

### Refund rules and limits

The refund command requires an explicit reason (`pos-operations.ts:329-334, 1550-1575`) and a closed sale. It sums positive safe allocation amounts, caps total cumulative refunds at the captured sale `netTotalCents`, requires each allocation's `paymentId` and `method` to match original captured payment, and separately caps cumulative allocation for that payment at its original `netAmountCents` (`:1275-1343`). Thus returned cash change is never refundable value, repeated refunds cannot overdraw a sale or a payment, and original payment/tender/order facts remain unchanged. The schema has no processor response, refund tender, refund external verification field, tip allocation, inventory compensation, or void action. Treat this as a manual append-only refund record; card/transfer refund completion remains unverified unless a later processor integration explicitly proves it. Tip refunds must remain unsupported until an explicit separate tip allocation policy is added; the current cap intentionally references food/net payment amounts only.

## Role and capability matrix

The command must satisfy both the server's current, verified device capability and current database-derived role. Client `authority.capabilities` is only a test/reducer input and is not authority in the RPC (`pos-operations.ts:1346-1403`; server contract `:42-44`). Current app policy (`src/access/role-policy.ts:70-110`) and operation tests/contracts yield:

| Action | Dueña | Encargado | Barra | Mesero | Required current device capability |
|---|---:|---:|---:|---:|---|
| Open/edit/details/split | yes | yes | yes | yes | `openOrder` |
| Apply discount | yes | yes | no | no | `discountWithReason` |
| Checkout | yes | yes | yes | no | `checkout` |
| Refund closed sale | yes | yes | no | no | `refundSaleWithReason` |
| Send preparation ticket | yes | yes | yes | yes | `openOrder` |
| Advance preparation | yes | yes | yes | yes | `prepareOrder` |

The operation map assigns checkout to `checkout`, refund to the special `refundSaleWithReason`, open/edit/split/prep-send to `openOrder`, prep transitions to `prepareOrder`, and discount to `discountWithReason` (`pos-operations.ts:312-350`). Do not treat a role badge or a saved client list as current access: the RPC must re-read/lock active membership, session, branch/device binding, capability/revocation and cash lease, check them before duplicate lookup, and fail closed after role loss. The server proposal requires lease for cash-register devices and no lease for preparation-only devices (`pos-operations-server-v1.md:42-47`).

## Recommended atomic RPC transitions

Keep `append_pos_operation_v1(p_command jsonb, p_session_id uuid, p_lease_id text)` as the only mutation boundary for this family. Use private operation commands/heads/events/projections and no direct client DML/SELECT; definer functions use empty search path, qualified object names, revoked PUBLIC execution, and derive principal from `auth.uid()` (`pos-operations-server-v1.md:25-39`).

For a new checkout, within one transaction: strict-validate the exact envelope and payment/line/discount fields; verify current authority before looking up command ID; serialize command ID; derive the required order/sale/preparation refs from current projections; create revision-zero placeholders for new sale; lock all heads in canonical `(branch,kind,id)` order; re-read projections and validate every expected revision; verify open order, source-linked prep guard, sale ID absent and all total invariants; run a deterministic server reducer; insert immutable command, order and sale event revisions, updated order/sale heads and projections, and branch sequence; return a receipt only after commit. Do not advance the guarded preparation head. Any late failure rolls back all rows and returns no receipt. Exact retry content (same action/payload/reason/occurredAt/expected refs/actor/device/branch) gets the original sequence/time only after today's authority checks. Reusing the ID with changed content conflicts.

For a refund, the same command/auth/idempotency/revision boundary locks only the sale head; re-read current sale and validate status, refund ID uniqueness, reason and all original-payment allocations while locked; append exactly one refund to the immutable sale history, bump its revision once, and commit. Two tabs refunding against the same revision serialize: one can commit and the other gets a non-acknowledgement HTTP 409 revision conflict; it must re-read remaining allocations and be explicitly reconciled, never automatically replayed with a fresh amount/ID. A committed response lost in transit is retried unchanged with the same command ID. A sale/refund ID collision under a different command is a business conflict, not success.

The contract already specifies current auth before duplicate, canonical command JSON comparison, exact action-derived ref set, deterministic lock order, expected revision comparison after locks, reducer-derived projections, one-transaction writes, and `PT409` with only `{kind,id,expectedRevision,actualRevision}` and no receipt (`pos-operations-server-v1.md:40-53`). Multi-aggregate checkout writes one shared branch sequence to both the order and sale; the existing operation read cursor/page algorithm must return every row with a boundary sequence or use a composite `(sequence,aggregate_id)` cursor before this family is exposed (`:65-67`).

Server must store server `received_at`/sequence separately from command `occurredAt`. The v1 envelope time is client-supplied, strictly parsed canonical UTC; this is useful audit context but not proof of a trustworthy device clock (`pos-operations-server-v1.md:69`). Never show it as server settlement/processor time.

## Read, privacy, local commit and recovery requirements

Customer contact is copied into both order and sale. Raw command/projection reads can therefore expose name, phone and delivery address alongside prices, discounts, payments and refunds. Keep the new operation tables private with RLS enabled/no direct access. Session-bound read RPCs should re-check current actor/session/role on every page and derive branch scope from the session. A preparation view excludes customer contact, money, discount/payment/refund data and raw command history; a cash view returns only information needed for the caller's authorized work; Dueña/Encargado report access can return financial facts. Do not widen v118 raw command RLS (`pos-operations-server-v1.md:17-19, 61-67`).

On device, append the complete local operation transaction (command + deterministic projections/heads/events) before UI success. Only set a durable-server receipt after an authenticated append RPC success response; offline, network timeout, stale revision, authorization denial and rejected late transaction each have distinct pending/blocked/conflict/error states. On timeout, keep the same command ID/content and retry it; on 409 keep exact command as blocked intervention work, and don't silently rebase money. Pending checkout/refund commands upload only after their original actor reauthenticates and current authority still permits the action. On cold start verify full order+prep+sale+refund replay and persisted projections; a draft-only local restore can resurrect a paid account or lose its payment/refund (`docs/execution/EVL-126.md:11-13, 29-36, 47-61`).

The real POS is not yet wired to `PosOperationsJournal` or this RPC. Legacy secure checkout sets `sync: 'acuse_desconocido'` and uses `this.up` to localStorage (`PosApp.jsx:1190-1272`); network/connectivity strings are not a receipt. Do not reinterpret that state as durable server acceptance. The existing recovery contract also forbids CSV/report exports being presented as a whole-state restore format (EVL-127 slice); checkout recovery needs complete journal replay/read, not report import.

## Cross-family blockers before checkout/refund can safely be enabled

- **Preparation/kitchen:** checkout guards the linked preparation revision and copies `preparationId` to the sale while leaving preparation unchanged. This is deliberate because payment and kitchen are independent. The server read path must include the latest prep link/revision and preserve split-linked shared preparation. Cancellation/refund must not cancel or re-enqueue work still needed by a sibling/paid account. Current EVL-126 server family has no preparation reducer/read integration; do not switch UI checkout to the RPC until preparation send/progress/cancel and independent reads/replay can represent the ticket (`pos-operations-server-v1.md:45-47, 82-84`).
- **Split (EVL-189):** split touches source order, revision-zero child, and shared preparation; it copies captured line facts, apportions discount, and carries lineage. Checkout must work for either child without duplicating/closing preparation. Preserve source/child/preparation IDs in both sale and preparation; no payment totals may be recreated from changed live catalogue data. Known-tax partial split remains blocked by missing tax basis. Finish and verify atomic split before enabling checkout for accounts that can be split.
- **Customer credit/prepaid/birthday:** operation-v1 customer data is only copied contact `{name,phone,address}`; no stable `customerId`, customer account aggregate, credit method, prepaid redemption, credit limit, or redemption identity exists (`pos-operations.ts:63-67, 69-78, 220-245`). The separate customer profile/ledger family does not currently make a checkout+customer-balance mutation atomic. A cash/card/transfer checkout can preserve the existing contact snapshot, but credit or prepaid sale must be rejected until one command includes expected customer revision and atomically appends sale + customer debit/redemption with unique cycle/retry protection. Birthday eligibility is preview only and cannot create a discount or redemption. Never add a browser-only “charge account” payment method or infer a credit balance from a stale profile.
- **Catalog/tax:** no authoritative catalog or tax tables are currently applied. Captured prototype/legacy values can be preserved and reconciled, but cannot support a production price/tax provenance or invoice claim. Tax's amount basis (inclusive/exclusive and how discounts affect it) needs a separate versioned policy before calculations or partial allocations.
- **Compensation/inventory/provider:** `sale.refunded` is a manual sale-level allocation only; it neither calls payment provider nor reverses kitchen/inventory. Existing `sale-compensation.js` appends local manual refund/void evidence and marks inventory compensation pending, but is not the server operation or trusted provider action (`src/domain/sale-compensation.js:16-78`). Exact refund/void or recipe-consumption reversal requires the original recorded consumption/payment source, not today's menu/recipe. No operator UI should claim that a bank refund or stock restoration succeeded.

## Recommended enablement order

1. Resolve the tip/legacy payment bridge and make TypeScript and SQL tip constraints identical. Pin tax/price evidence rules and explicitly disallow unsupported tax claims/refunds.
2. Implement SQL validation/reducer for checkout only behind the new private tables/RPC, with order+sale+optional prep refs, one-transaction differential/local-Postgres tests, and safe multi-row read pagination.
3. Implement refund as a separate allowlisted reducer/RPC branch against sale revision only; test cumulative/per-payment limits and two-refund races, distinguish local/manual capture from actual provider reversal.
4. Complete prep/split/customer dependencies and sanitize point-in-time reads/recovery. Then integrate local journal and POS UI one family at a time, with visible local-commit vs server-receipt states.
5. Only after isolated hosted race/revoke/offline-reopen/retry tests pass can checkout/refund be described as server-durable. No current source reviewed here proves that acceptance state.
