# EVL-189 — Split an open account by captured quantity

## Implemented checkpoint

Open accounts can now be split by quantity using integer centavos. The default proposal allocates about half of the captured units to a new account. Before confirmation, the operator sees each account's item quantities, subtotal, discount, and total, along with the conserved combined subtotal, discount, and total. Explicit planner selections are represented by a `Map` or an array of `{ lineId, quantity }` records; arbitrary line IDs are never used as object keys. Full operator selection controls remain EVL-155 scope.

Captured unit prices stay unchanged. A partial line retains its modifier and note association, tax snapshot, quantity, and recomputed captured line total. The order-level discount is allocated in proportion to each account's subtotal, rounded half-up to centavos for the new account, with the exact remainder kept by the source. This preserves the original combined discount and total.

Confirmation checks the current `openOrder` authority and rereads the source from live state and the scoped local record. It rejects malformed split history or collections, a missing, changed, paid, or conflicting source, and a preview whose folio counter has since advanced. The folio picker starts from the newer stored sequence and skips any folios already present. A stable operation ID is held through a failed-write retry and persisted with the source/child link. The split, pending operation, and next folio are written atomically against the latest local record, preserving unrelated orders, sales, kitchen tickets, station draft, and table settings. React state then refreshes from that committed record. Repeating a successful confirmation recognizes the stored operation instead of creating another child.

Both accounts retain the original `preparationFolio` and are marked as sharing preparation. Splitting does not change or duplicate the kitchen ticket. Resuming and saving either account keeps that linkage; checkout and sale history carry the preparation folio, shared-preparation marker, split lineage, and captured line snapshots forward. Cancelling one shared account leaves the shared kitchen ticket intact for review rather than cancelling preparation required by its sibling.

## Verification

- Planner tests cover a $100 subtotal with a $20 discount, partial quantities, zero and order-level discounts, centavo rounding, quantity and line-total snapshot updates, tax conservation, captured prices/modifiers/notes, safe IDs, and malformed/unsafe inputs.
- POS component tests verify the allocation preview, `$100 − $20 = $80` combined totals, persisted account split, stable operation identity, one-write failure/retry, duplicate-confirmation safety, and cancellation of the preview without changing the account or folio sequence.
- POS component tests verify that malformed histories fail visibly, newer unrelated local changes survive confirmation and refresh live state, and both stale and newly advanced folio sequences are handled monotonically.
- POS component coverage also charges the child account and verifies that checkout and sale history preserve its captured line snapshot and shared preparation lineage while the original kitchen ticket remains unchanged.

## Remaining gates and limits

This checkpoint commits to the prototype's single local-storage record only. It does not claim durable cross-device atomicity, remote conflict resolution, or server-side account version checks; those remain EVL-118/126 integration gates. Shared preparation is linked and protected from whole-ticket cancellation, but granular preparation/inventory compensation when siblings have different payment or cancellation outcomes still requires EVL-126/129. Full operator selection controls remain EVL-155. No account move/merge flow is introduced.
