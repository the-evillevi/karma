# EVL-129 — recipe configuration checkpoint

This checkpoint adds a validated recipe ledger, integer-unit preparation and compensation planners, and a Spanish operator configuration panel. Operators choose products and inventory items by explicit IDs; there is no name-based automatic mapping. A recipe, finished product by piece, or explicitly uncontrolled product is a recorded choice. Modifier behavior is captured for each exact `(groupId, optionId)` pair and supports no inventory effect, multiple added ingredients, or ingredient substitution where the menu group only permits one selected option. Recipe history snapshots names, item identifiers, units, quantities, actor, time, reason, evidence, source revisions, and the preview used at publication. Previous versions remain immutable and are visible read-only while editing.

The panel previews base quantities and each modifier scenario against current ledger balances before publication, displays provenance and validation warnings, and requires explicit preview acknowledgement. Publication is limited to verified Owner/Manager authority, rechecks the current authority at the mutation boundary, rejects stale recipe/menu/inventory revisions, and writes the append-only catalog before reporting success. Identical stable-command retries do not duplicate history. A failed local write leaves the editor open for retry with the same command identity. Corrupt stored recipe history fails closed. Ordinary POS saves preserve the latest stored recipe catalog, and publication refreshes operational state from the latest scoped record before updating the mounted POS.

Recipe definitions and previews are currently persisted locally. The bundled menu and initial stock are still prototype fixtures with unverified business provenance; they are labeled as such, do not auto-map products, and cannot qualify a recipe for automatic stock consumption. The editor does not change menu prices, existing tickets, sales, or stock. It does not create or dispatch kitchen tickets. Domain preparation planning accepts captured product, quantity, and modifier IDs and produces integer base-unit movement candidates from immutable recipe snapshots; the plan begins `not_applied`. Compensation planning uses the actual allocations of a committed preparation record rather than recalculating a live recipe. Neither planner writes inventory.

EVL-126 remains a hard gate for enabling recipe-driven stock movement: send, exactly-once consumption, inventory compare-and-write, operation identity, and cancellation/refund compensation must commit atomically with durable authority. Until that boundary exists, no SEND, checkout, cancellation, or refund path may claim that a planned movement was applied. EVL-129 is not production acceptance while cross-device storage, authoritative physical stock provenance, and atomic operational wiring remain open.

Validation for this checkpoint: recipe-domain tests (6), actual configuration UI tests (6), the shared `pnpm test:domain` suite (104), all component tests (108), targeted Prettier check, standard production build, and PWA build. The UI tests cover explicit product/item mapping, exact modifier group/option mapping with multiple ingredients, immutable history across reload, unchanged stock, role changes, stale source revisions, corrupt history, and failed-write retry. These checks do not prove cross-device persistence or EVL-126 behavior.
