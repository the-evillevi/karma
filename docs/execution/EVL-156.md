# EVL-156 implementation checkpoint

This is a bounded implementation checkpoint for EVL-156, based on the approved palette and interaction contract in [`DESIGN.md`](../../DESIGN.md). It is not a completion or visual-approval claim. Full mapping, integration with EVL-116, and desktop/mobile review remain open.

## Implemented

- Added official shadcn/ui configuration for the existing JavaScript Vite app (`components.json`, `jsconfig.json`, `@` alias) and Tailwind CSS v4 through the Vite plugin. The generated components use the Radix base and JavaScript/JSX output. The two existing HTML entries remain intact.
- Centralized the shadcn semantic color variables and radius aliases in `src/styles.css`, using only the values recorded in `DESIGN.md`. Primary buttons use toasted brown with paper text; outline controls use the stronger primary boundary where the border carries meaning; destructive controls use charcoal/paper. Focus uses a 2px toasted-brown ring with a 2px offset. No dark theme or new hue was added.
- Added generated shared `Button`, `Card`, `Badge`, `Input`, `Textarea`, `Label`, and Radix `Dialog` primitives in `src/components/ui`. The Button supports primary, secondary, outline, ghost, link, and destructive variants, a 44px minimum target, visible focus, disabled and busy states, and `asChild`. Form controls have persistent label composition, 44px targets, primary boundary contrast, and visible focus. `Badge` includes neutral, pending, success, and conflict variants. Button and focus-managed wrappers forward refs so Radix keyboard behavior works.
- Replaced kitchen filter buttons, kitchen action buttons, kitchen status pills, and kitchen card wrappers in `src/ComandaApp.jsx` with shared primitives.
- Replaced POS category filters, discount action, order-save/send/cancel actions, and checkout CTA in `src/PosApp.jsx` with shared Buttons. The empty-order CTA remains keyboard-operable and still calls the existing validation/toast path.
- Replaced the existing POS confirmation overlay with the Radix Dialog. Existing state callbacks remain authoritative; labels are associated with fields, field errors are announced, Escape closes the uncommitted dialog, focus returns to the invoking control captured on open, and the close control meets the 44px target.
- Added `components-demo.html` as a small component variant story with button, badge, card, and dialog states. The demo is available at `/components-demo.html` while Vite runs.
- Added repeatable checks covering dialog keyboard open/dismiss/focus restoration, the disabled/`aria-busy` button contract, and an input's label/error association. The POS integration test mounts with no dialog, signs in using the seeded cashier PIN, opens the real role-warning dialog through the restricted navigation action, and verifies Escape returns focus to that exact invoking button.

## Verification evidence

- `pnpm test`: 1 test file, 4 tests passed. The demo-level test first exposed missing ref forwarding. The POS integration test then reproduced that Radix's normal trigger restoration cannot restore focus for this app's programmatically opened dialog, so the POS captures the active launch element and restores focus on close. All four checks pass without React ref warnings.
- `pnpm build`: passed for the POS, Comanda, and component-demo HTML entries.
- `pnpm dlx shadcn@latest info --json`: confirms Vite, Tailwind v4, JavaScript, Radix base, Lucide icons, and the configured `@/components/ui` and `@/lib/utils` paths.
- Chrome accessibility-tree inspection of `/components-demo.html` showed the Spanish heading, named enabled/disabled buttons, four text-bearing status badges, labeled controls, and an accessible dialog trigger. This was a structural check, not a desktop/mobile visual sign-off.

## Remaining migration and review gates

This checkpoint does not include the shadcn mappings for Tabs/ToggleGroup, Select, AlertDialog, Sonner, Table/ScrollArea, Switch, Alert, Avatar, Progress, InputOTP, Separator, Sidebar, Sheet, or Drawer. Use those only where they fit the existing business flow; do not replace a flow solely to match a component inventory. EVL-158 owns the broader responsive shell and mobile navigation.

Before calling EVL-156 complete, reconcile dependencies/configuration with EVL-116, continue replacing duplicated controls in the remaining modules, run representative POS, inventory, recipe, open-order, report, configuration, checkout, and Comanda flows, and verify rendered desktop and mobile layouts with root. Record actual visual findings rather than treating the demo or build as visual evidence. Keep the Linear issue open until those gates are met and team acceptance is recorded.

## Migration note for new UI

Import shared components from `@/components/ui/*`; use `Button` variants and `Badge` status variants before writing new repeated style objects. Compose cards from `Card` primitives and use `Dialog`/Radix focus behavior for modal work. Use `cn` from `@/lib/utils` to combine Tailwind classes. Add new semantic colors and radius decisions to `DESIGN.md` first, and keep app-specific event/state logic in the app component. New controls need persistent labels, keyboard focus, disabled/loading/error states, and a test or demo covering their user-visible states.
