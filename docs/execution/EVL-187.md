# EVL-187 — cancellation audit and history

Both saved-account and station cancellation now use one confirmation path. It checks the current authorization when confirmation executes, requires a 1–250 character reason, and preserves folio, captured items/prices, original creator/time, cancelling actor ID/name, ISO timestamp, and an audit entry. Reopening an account into the station no longer makes its cancellation disappear from history. Unsaved orders with captured items also receive a folio and cancellation record.

Confirmation compares the source with current memory and persisted browser state. Paid, cancelled, conflicting or changed accounts require review rather than a stale cancellation. A stable cancellation command ID makes repeated confirmations idempotent; unrelated persisted kitchen/history records are preserved. The record is written before clearing the station or announcing success, so a failed local write leaves the account open.

This slice still uses browser-local prototype storage. EVL-118 supplies verified runtime authorization; EVL-126 must persist the operation in the real actor-bound command/outbox transaction, and EVL-129 must apply inventory compensation exactly once. This command ID is a local idempotence key, not proof of remote synchronization or cross-device atomicity. No production acceptance is claimed for those remaining gates.

The preceding combined component suite passed 39 cases before adding the final actual-resume case. The four-entry build and client credential scan passed after the final eight-case suite.
