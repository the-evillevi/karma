# EVL-119 checkpoint: catalog domain commands

## Delivered in this checkpoint

`src/catalog/catalog-domain.mjs` provides structural validation for the canonical `karma.catalog/v1` format and pure category/product commands. Commands accept an envelope with `commandId`, `actorId`, `occurredAt` (ISO-compatible date), `type`, and the type-specific fields. Supported types are `category.create`, `category.edit`, `category.reorder`, `category.setActive`, `product.create`, `product.edit`, `product.reorder`, and `product.setActive`. Product prices are integer MXN centavos. IDs are stable and immutable; commands do not delete records. A command appends an audit event, advances catalog revision, and returns a new frozen catalog snapshot without mutating the input.

Exact retries with the same command ID and payload return the already-applied catalog without another event. Reusing a command ID for a different payload fails. Callers must provide actor identity from an authenticated source. This is a deterministic domain contract, not trusted authorization, durable audit storage, or a secure replay lock; the server/storage foundation must enforce those properties.

The canonical seed now includes `active` for products, distinct from `available` (temporary stock or out-of-stock state), plus an empty `auditEvents` array. Product and category disablement are preserved as data. `src/catalog/runtime-adapter.mjs` maps canonical MXN-centavo fields to the current prototype POS data shape and sets runtime `available` false whenever the product or its category is inactive. It also preserves `priceCents` alongside the legacy peso number and rejects any amount that cannot round-trip exactly. Runtime output carries `catalogInfo.demoOnly` while business validation remains closed.

The adapter is an integration seam only; it is not wired into the PWA and does not persist edits. The existing app still loads its prototype data. Reopening historical orders continues to depend on captured line snapshots; the domain commands never rewrite an existing order or ticket, and this checkpoint does not migrate historical order storage.

## Validation

Run:

```sh
node --test src/catalog/catalog-domain.test.mjs scripts/catalog/catalog-normalizer.test.mjs
node scripts/catalog/normalize-seed.mjs --check
```

Tests use the committed demo seed and synthetic command inputs. They cover structural validation, category/product create/edit/reorder/activation, invalid names/category references/centavo amounts, immutable inputs and order snapshots, replay conflicts, category/product sale blocking, audit metadata, and exact centavo mapping.

## Acceptance and remaining gates

This is a partial domain checkpoint, not EVL-119 completion. The following dependencies remain before a reviewable user workflow exists:

- EVL-116 must provide the reviewed PWA/runtime and local persistence integration point. The adapter boundary is `adaptCatalogForRuntime(catalog, existingRuntime)`; catalog commands are `applyCatalogCommand(catalog, command)`. Wire these at the actual data-loading and management paths once that foundation is reviewed.
- EVL-118 must provide trusted role enforcement and audit persistence. A client-supplied `actorId` and in-memory frozen event array are not security controls.
- EVL-126 must define the synchronization boundary and conflict behavior. This module makes no cloud-sync claim.
- The business gate in `catalog/catalog.json` remains false pending source reconciliation and Carlos's validation. The current seed is demo-only and must not be treated as approved commercial data.
- The sales workflow must keep immutable line price/name snapshots and check the adapter's effective `available` state before adding new lines. Existing captured ticket/order values must remain unchanged when catalog prices change.

The implementation is intentionally isolated under `src/catalog`; it does not modify app entry points, `PosApp.jsx`, package manifests, or migrations.
