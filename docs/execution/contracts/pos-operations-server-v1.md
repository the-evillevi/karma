# EVL-126 forward server support proposal

## Candidate implementation checkpoint

The candidate forward migration `20260930000100_evl126_pos_operations_v1.sql` and gated synthetic hosted proof are in this branch for review. The follow-up migration `20260930000200_evl126_revision_conflicts.sql` changes only business revision-conflict errors from SQLSTATE 40001 to PostgREST's HTTP-409 `PT409` mapping, retaining the same safe details and append logic. The candidate supports only opening and editing open orders (`order.opened`, line add/change/remove, and details change), plus a session-bound cash-register read view. It derives projections on the server, checks current session/device/lease/membership before retry lookup, and rejects all unimplemented action families and catalog-versioned claims. The forward migration pair is not applied or deployed, and the POS UI is not wired to it. This is not evidence of production durability or successful remote synchronization.

The hosted lane is `pnpm test:pos-operations-server:e2e` and stays skipped unless `SUPABASE_V126_TESTS_ENABLED=1` is explicitly set. It reads only the approved private fixture's URL, anon key, and synthetic user credentials; it never uses the service-role key. Root will run that lane only after reviewing and applying the exact migration candidate to the isolated project.

`pnpm test:pos-operations-server:local` applies immutable migrations 114/118 and both candidate 126 migrations to a disposable, network-isolated Supabase PostgreSQL 17.6.1.166 container, then checks private-table ACL/RLS, RPC grants, supported order open/edit/read, strict payload validation, exact retry, stale-revision PT409 without state changes, and late transaction rollback/retry. It never connects to a hosted project and removes its own container on exit.

The sections below describe the applied baseline, candidate boundary, and remaining contract gates. No remote writes or deployment were performed for this checkpoint.

## Current boundary

EVL-114 migration `20260929000100` is applied and immutable at SHA-256 `4cbd6999a2d8f4151769da2b923ed001474ea502192470ada15d86afd0cdc8d3`. EVL-118 migration `20260929000200` is applied and immutable at SHA-256 `44d5214315b9a16261bf6ec66eb0a4c002c4e6515df3bd6bb6fec1bf3b056406`. Do not edit or replace either migration; make all additions in a new forward migration.

`command_batches` stores one EVL-114 batch with a single `aggregate_id` and ordered event array. Its v118 append RPC checks `auth.uid()`, current bound device session, active branch membership, registered device, current cash lease, role, device capability, and event allowlist. It does the authorization checks before insert/duplicate resolution; an exact duplicate returns its original `received_at`, while changed content conflicts. However, its immutable row contains `lease_id`, its event allowlist is the old EVL-114 schema, it has no operational aggregate heads/projections or expected-revision transaction, and it cannot atomically represent the EVL-126 multi-aggregate split/checkout/preparation/refund transitions. Do not reuse or widen this RPC for operation-v1 commands.

EVL-118 grants authenticated users raw `command_batches` SELECT under a role-limited policy: Dueña/Encargado can read all branch commands, while Barra/Mesero can read their own. That is not a safe shared kitchen or cash work read model. No dedicated sanitized operational read RPC currently exists. The current applied migrations also contain no authoritative catalog/tax tables.

The local EVL-126 command contract has 13 version-1 actions: open/edit/details, discount, preparation send/transition/cancel, account cancel/split, checkout, and sale refund. Each command includes original actor, branch/device, stable command ID, time, action payload, reason where required, and canonical expected revisions for all target/read aggregates. Sessions and leases are transport authorization and intentionally are not business-command identity. The local reducer enforces current capability/role on append and retry, but replays historical commands without reauthorizing old actors. It preserves captured facts with prototype/unknown provenance and never promotes them to verified catalog or tax facts.

Current role policy: all four roles can open/split orders; Dueña/Encargado/Barra can checkout; only Dueña/Encargado can discount, cancel, cancel preparation, and refund; all roles with `prepareOrder` may advance preparation. Action-specific device capability still applies. Menu/inventory/customer directory, void/provider settlement, tip refunds, shared-preparation line edits, and ambiguous known-tax partial splits are outside this operation schema.

## Recommended forward-only database boundary

Add separate `pos_operation_*` objects; leave EVL-114/118 objects and RPCs untouched. Keep all new tables inaccessible to `anon` and `authenticated` directly, with RLS enabled, no client table DML, and only narrowly granted security-definer RPC execution. Every definer function should set an empty `search_path`, qualify objects, revoke default `PUBLIC` execution, and derive the actor from `auth.uid()`.

A minimal schema is:

- `pos_operation_commands`: immutable full canonical business command JSONB, indexed command ID, branch, original actor, device, schema version, server sequence, and server `received_at`. Enforce the duplicated indexed columns equal the command envelope. Never put session ID or lease ID inside the canonical command/hash; those are checked as current transport context on every call.
- `pos_operation_aggregate_heads`: `(branch_id, kind, aggregate_id)` primary key, current revision, and last command ID. Use a revision-zero row for new aggregate creation so concurrent inserts can be serialized.
- `pos_operation_aggregate_events`: one immutable row per aggregate whose revision advanced, carrying branch/kind/id/revision, command ID, and server sequence. A unique `(branch, kind, aggregate, revision)` constraint prevents two commands claiming the same revision.
- `pos_operation_projections`: private reducer-derived state keyed by branch/kind/id with the same revision/last-command metadata as its head. These rows are never accepted from the browser and never directly returned through table SELECT.

All command, event, head, and projection writes occur in one PostgreSQL transaction. An identity/sequence value may have gaps after rollback; acknowledgements need a stable committed sequence, not gap-free numbering. Store only the canonical command and necessary audit metadata; do not persist a client projection, a client capability list, a session/lease in command identity, or an arbitrary client event list.

Expose one `append_pos_operation_v1(p_command jsonb, p_session_id uuid, p_lease_id text)` RPC. Return a typed result with command ID, `inserted` versus `identical-retry`, server sequence, and server received time. Never return a receipt on any denial, conflict, or rejected action. The browser records a local server receipt only after receiving this authenticated committed acknowledgement.

## Append and retry algorithm

1. Parse and strictly validate the whole command envelope before database changes: exact keys, v1 schema, bounded UTF-8 size, canonical UTC time, bounded IDs, safe integer cents (`<= 9007199254740991`), `MXN`, exact action payload allowlists, reason lengths, array/count limits, unique identities, and canonical unique aggregate-ref ordering. Reject projections, sessions, leases, roles, capabilities, credential fields, unknown actions, and action fields escaping their family.
2. Derive the principal with `auth.uid()`. Require it to equal `command.actorId`; require its active membership in `command.branchId`; verify the caller-supplied current session is unrevoked, unexpired, and exactly bound to that actor/branch/device. Recheck active device and matching capability/revocation. For a cash-register device require the currently active lease matching this session; for a preparation-only device reject cash lease data. Derive the current role from the locked database membership and apply the action/role/capability matrix above. Do all of this before looking up a duplicate command so revocation/demotion/new actor never receives a stale success acknowledgement.
3. Serialize lookup by command ID (transaction advisory lock or an insert/unique-key strategy), then compare an existing command against the complete canonical business JSONB. Exact content returns the stored sequence/time only after the current authority checks. Changed action, payload, reason, revisions, actor, branch/device, or occurrence time returns a conflict. A renewed session/lease alone does not change immutable command identity. Do not compare old expected revisions before recognizing an authorized identical retry.
4. For a new command, derive the exact required aggregate set from action and current projections, not from a client-supplied changed-aggregate list. For example checkout touches the order and new sale and guards linked preparation; a split touches source, new child and any shared preparation; a line edit guards and advances linked nonterminal preparation; a refund touches the sale. Require the command refs to equal this derived set, including read-only dependencies.
5. Insert missing revision-zero head placeholders, lock all expected heads in deterministic `(branch_id, kind, aggregate_id)` order, then re-read current projections. Compare every current revision with its expected value. Validate prior-state links/status and action-specific invariants while holding those locks. If stale, return a non-acknowledgement `OPERATION_REVISION_CONFLICT` with only safe expected/current revision metadata; the local queue retains it for intervention.
6. Run a server-owned, deterministic action reducer against those locked projections. The reducer derives the next projections and changed aggregate set; it does not accept a client-supplied after-state. Validate that each changed revision advances exactly once, untouched read guards do not advance, and no operation changes more than its exact target set. Insert the immutable command, aggregate-event rows, heads, and projections only after every action validator succeeds. Any failure rolls back all business writes. For conflict reporting, either return a safe conflict result without business writes or write a separate minimal diagnostic containing only IDs/revisions/code; never persist the failed full PII-bearing command as an accepted operation.

The client-visible stale-revision error is SQLSTATE `PT409`, HTTP 409, message `OPERATION_REVISION_CONFLICT`, with only `{kind, id, expectedRevision, actualRevision}` in detail. It has no command receipt and is not an automatic retry: keep the immutable command as blocked work for explicit reconciliation. Never use application-raised SQLSTATE `40001`; PostgREST 14 treats it as transient and can retry the RPC indefinitely ([Supabase troubleshooting guidance](https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b)). The old EVL-114 `command-sync` queue is not this operation API; any future bridge must explicitly preserve PT409 as a conflict rather than retrying it as an ordinary transport failure.

The reducer must check internal accounting and lifecycle invariants, not only role. It must preserve order/customer/contact/discount/reason/actor history, shared preparation lineage, closed-sale/tender/change/tip snapshots and refund allocations. Checkout/refund never rewrite historical payments or reopen a sale/account. Known money is exact safe cents and cash tender/change reconciles. Unverified card/transfer remains manual-unverified. The current PosApp payment `netAmountCents` includes allocated tip, while operation-v1 separates `tipCents`; the bridge must reconcile this explicitly and retain gross tender, net payment, change, and tip without copying incompatible fields. Unknown catalog/tax facts stay explicitly unknown/prototype; the server cannot use them as evidence of a correct sale price, tax calculation, invoice, or provider settlement. The current schema has no authoritative menu/tax version source, so reject a client claim of `catalog-versioned` provenance until a version is checked against a server-owned catalog; preserve prototype/legacy/unknown labels and values without upgrading them. Before production reporting or tax claims, add authoritative catalog/tax schemas and version checks. Never take a client-supplied projection or label prototype data catalog-verified.

The existing TypeScript reducer is the executable contract but PostgreSQL cannot import it. The database therefore needs an explicit server reducer/validator, with shared fixtures and differential tests against TypeScript for each action before enabling that action. An Edge Function may wrap transport and rate limits, but it must not become a way to trust browser-supplied projections; the transaction RPC remains the authoritative revision/transition boundary.

## Smallest safe implementation slice

Start with migration tables/RPC plumbing and an allowlist limited to the fully validated open-order family (`order.opened`, line add/change/remove, and details change) for synthetic hosted proofs. Reject all other actions with an unsupported-operation error. This establishes authenticated current-authority checks, immutable identity/idempotency, revision-zero creation, canonical locks, server-derived open-order projections, and rollback without prematurely implementing financial or kitchen facts. Do not wire POS UI to this partial server API: current local replay and server reads still need all close/cancel/split/refund/preparation families before startup can safely restore operational state.

Then add, separately test and review: discount/cancel; preparation and shared lineage; atomic split; checkout/tenders/tips; and refunds. Each action remains unavailable server-side until its payload validator, exact aggregate set, reducer, rollback, and role tests are complete. The first open-order slice must reject client `catalog-versioned` price/tax claims because no authoritative catalog schema exists yet; it can preserve only captured prototype/legacy or unknown provenance. Integrate local sync and UI only after the full operation family set used by the UI can be replayed atomically.

## Sanitized read boundary

Keep the command log, heads, and full projections private. Add dedicated session-bound read functions that recheck current actor/session/device/role on every request and derive branch scope from the verified session, not a caller-supplied branch or cursor. A preparation work view can return only ticket/order IDs, line/modifier labels, notes, preparation status, and bounded transition metadata; exclude customer name/phone/address, totals, prices, discounts, payment/refund data, raw commands, roster/PINs, and credentials. A cash work view may return the account/contact/table/line/price facts the role needs, but not staff secrets. Report/history access remains Dueña/Encargado. Use an opaque or validated branch-scoped sequence cursor with bounded page sizes; cross-branch, stale-session, malformed cursor, and revoked identity cases fail closed. Do not broaden EVL-118 raw-command RLS.

The candidate cash read RPC is a live change feed, not a point-in-time snapshot spanning multiple pages. It orders visible aggregate updates by the branch sequence, whose row lock serializes sequence allocation through commit. Therefore an operation committed after a page snapshot receives a sequence above that page's cursor and remains eligible on a later request. A concurrent update can also cause an order returned on one page to reappear later with a newer revision; consumers must merge by `orderId` and keep the highest revision. The hosted proof races an append against a page read and continues from the returned cursor to verify the new order is not skipped.

The current server allowlist changes one order aggregate per command, so a server sequence cannot be split across multiple order rows by a page limit. Before enabling a multi-aggregate server action, change pagination to a composite `(sequence, aggregate_id)` cursor or return every row sharing the boundary sequence before advancing the cursor; otherwise one page could skip a second aggregate from the same command.

The server timestamp parser is stricter than JavaScript date parsing: it accepts only the bounded UTC `Z` syntax and rejects calendar/time values that PostgreSQL would normalize, including `24:00`, leap seconds, and invalid calendar days. It compares the parsed UTC date and whole-second time back to the original prefix, then retains the original timestamp string so equivalent fractional spellings such as `.0Z` and `.000Z` stay byte-for-byte distinct command facts. The local reducer's parser is not evidence that every such timestamp will pass this server boundary.

## Acceptance proof before UI integration

Run against only the approved isolated `karma-pos` project using unique synthetic `.invalid` identities and root-owned private fixtures. The existing direct insert and applied-schema proofs stay intact. New tests should cover:

- Authenticated direct SELECT/INSERT/UPDATE/DELETE/TRUNCATE denial on every new table; anon denial; only the intended RPC grants.
- Valid owner/manager/barra/waiter cases for each supported action and denial for every unsupported action, role, or device-capability combination.
- Actor/branch/device mismatch, no JWT, inactive/demoted member, replaced or expired/revoked session, revoked device, expired/revoked/wrong lease. Specifically repeat an identical prior command after a known denial and assert it returns no receipt.
- Exact same-actor retry after session/lease renewal returns identical server sequence/time once; changed content under the same command ID conflicts; another actor cannot upload a queued command.
- Two devices/tabs with the same expected revision: one commit, one revision conflict, no double history or projection. Deterministic lock ordering avoids deadlocks for overlapping split/order/preparation commands.
- Multi-aggregate late failures prove full rollback of command, events, heads, and projections; retry after injected failure succeeds once.
- Malformed JSON types, unknown keys, oversized fields/arrays, unsafe/fractional/negative money, non-MXN, conflicting IDs, client projection fields, actor/capability/session/lease injection, malformed reasons, over-discount, duplicate IDs, bad contact requirements, unsupported known-tax partial split, impossible cash change, duplicate payment/refund IDs, refund-over-payment, and attempt to mutate/void/reopen a closed sale.
- Independent preparation progress after account checkout/cancel; shared split keeps one preparation lineage and does not reset kitchen progress.
- Read RPC role/capability matrix, cursor isolation, waiter prep view exclusion of contacts/money/raw actor history, cashier-needed account view, owner/manager report scope, and revocation between pages.
- Differential fixtures comparing server projections/head transitions to `src/domain/pos-operations.ts` for every supported command; exact local restart + original-actor reconnect and server receipt durability after response interruption.

Remaining after server RPC work: actual local sync wiring, safe complete boot/read merge, POS UI mutation integration by family, shared incremental operational views, authoritative menu/tax provenance, menu/inventory/customer/void/tip-refund actions, offline shell/device enrollment and recovery, and final hosted offline-close-reopen-revoke/receipt/conflict proof. Until these pass, EVL-126 stays partial and no production-sync/durable-sale claim is appropriate.
