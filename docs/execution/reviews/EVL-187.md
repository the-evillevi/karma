# EVL-187 — root code review with fixes

Root inspected both cancellation callbacks, kitchen projection rules, payment stale-source checks, persisted snapshots and acceptance criteria. The duplicated station path could remove a reopened account without a history record because resuming removed it from `open`. It also lacked a stable retry identity and source verification. The implementation now shares a single path, reconstructs origin from saved order/kitchen metadata, checks the live identity and source, bounds reasons, writes before success, and records a stable cancellation command ID. Review also fixed legacy restored-line identity comparison and prevented a stale folio sequence from colliding with an existing local record.

No blocking findings remain in this bounded prototype slice. Tests exercise actual mounted POS logic instead of only mirroring a helper: eight cases passed; combined predecessor regression suite 39 passed; four-entry build and credential scan passed. The final combined integration suite will run after the parallel access/order changes are reconciled.

## Acceptance criteria

- Met: manager/owner cancellation checks at execution; unauthorized Barra denial; reason validation and dismissal without mutation; actor, timestamp, original creator, folio, captured items and history for both saved/station/reopened paths.
- Met within local storage: retry/reload keeps one cancellation entry, stale/paid/conflicted accounts do not mutate, storage failure leaves the source repairable, and kitchen cancellation follows the authorized operation.
- Partially met: canonical verified-role enforcement depends on independently accepted EVL-118 integration. Secure storage keys are consumed when provided by that runtime.
- Not met: real durable command transaction/remote sync (EVL-126), inventory compensation once (EVL-129), and production recovery proof. A local operation key is not a cross-device transaction.
